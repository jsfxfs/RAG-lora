## 一、GPU / 模型类（首轮本地评测报废的元凶）

### 坑 #4：CUDA OOM 连环炸 ⭐ 本项目最惨烈的坑

**现象**：本地评测 64~79% 的题报 `CUDA out of memory`，acc 只有 16~23%，
整轮数据作废（留档为 `*.bak_oom`）。

**原因拆解**（一张 16G 卡的显存账）：

```
Qwen3-4B (bf16)      ~9.0 G  ┐
bge 编码器            ~1.3 G  ├─ 常驻 ~12.5 G
bge-reranker-large   ~2.2 G  ┘
长表格题 KV cache    +1.7~2.4 G  ← 装不下，OOM
                                  ← 更糟：一次 OOM 后显存碎片化，
                                     后续题连环失败
```

**解法（三招组合拳）**：

1. **模型生命周期管理**（核心）：检索和生成的显存需求错峰——
   ```
   改造前：bge + reranker + Qwen3 全程常驻（余量 3.5G）
   改造后：先把 100 题的检索全部做完
           → del bge, reranker + torch.cuda.empty_cache()
           → 生成模型独享整卡（余量 7G）
   ```
2. **输入截断**：超 6144 token 保头保尾截断（**尾部是问题，绝不能丢**）；
3. **OOM 后自愈**：单题 OOM 立即 `empty_cache()` 清碎片，不再连环炸。

**效果**：OOM 题从 ~70 降到 ~10（剩余是真·超长表格题，另行降 4096 补跑）。

> 📌 **通用教训**：多模型共卡时，先画显存时序图——谁和谁**真正需要同时在卡上**？
> 检索和生成天然可以错峰，这是 RAG 系统的结构性优势。

### 坑 #5：Qwen3 默认思考模式 ⭐ 差点制造错误结论

**现象**：base 模型 acc 仅 23%，rank16 正常——险些得出"LoRA 大幅提升 RAG"。

**原因**：Qwen3 chat template 默认 `enable_thinking=True`，base 输出大段
`<think>...`，在 512 token 生成上限内经常"还没想完就被截断"，既费显存又没答案。
rank16 因为学过简答风格的 QA 数据**自发不 think**，于是显得强。

**解法**：`apply_chat_template(..., enable_thinking=False)`，一行修复。

> 📌 **通用教训**：① 换新模型系列先通读它的 chat template 默认行为；
> ② 对比实验中一方异常低分，**先怀疑实验设置再下结论**——这个坑差点让
> 一个错误的正结果进汇报。

### 坑 #6：异常处理覆盖了 GPU 辛苦生成的答案

**现象**：裁判（API）调用失败后，本地 GPU 已生成好的答案被 `[ERROR] ...` 抹掉。

**原因**：`except` 里写了 `it["answer"] = f"[ERROR] {e}"` ——无条件覆盖。

**解法**：改 `setdefault`，只在**没有答案时**才写错误标记。

> 📌 **通用教训**：昂贵产出（GPU 生成的答案）和廉价产出（一次 API 判分）要分开
> 存储和保护，异常路径永远不该覆盖已成功的昂贵产出。同族坑 #6b：gen 失败题
> 在 judge 阶段 KeyError——对 error 题显式 `judge=0` 兜底。

## 二、长任务运维类

### 坑 #7：长任务中断即白算 → 三级断点续存

**现象**：评测进程被杀，跑了一半的配置全部重来（API 费白烧）。

**解法**：三级粒度的断点续存，一层比一层细：

```
Level 1  配置级    结果文件里已完成（非 partial）的配置直接跳过
Level 2  分段级    配置内每 20 题落盘一次（带 partial 标记）
Level 3  单题级    生成的答案每 10 题增量存 gens 区，
                  重跑按题目文本匹配复用（--fresh 也不清除！）
```

**实战救命两次**：① 首轮 OOM 事故中 vec/hybrid/hr 三配置结果零损失；
② hr_route 刚开始时进程被杀，续跑只补 hr_route。

**血的起源**：更早版本是"全部跑完最后统一写盘"——API 偶发超时把线程池炸掉，
已完成的 vec 结果**只留在日志里**，被迫从日志里抠数字。

> 📌 **通用教训**：凡是"跑一次 > 10 分钟或 > 1 元"的任务，写代码时第一件事
> 就是设计落盘粒度。**最后统一写盘 = 赌进程不死。**

### 坑 #8：nohup 后台进程的迷惑行为

**现象**：Ctrl+C 之后任务"居然还在跑"；SSH 断了它也不死；想杀杀不掉。

**原因**：`nohup ... &` 的进程免疫 Ctrl+C 和 SSH 断连，只认 `kill PID`。

**解法（项目最终约定）**：所有命令**单行、前台**运行，中断风险交给断点续存兜底
（靠机制免疫中断，而不是靠进程不死）。若必须后台：
`pgrep -af xxx.py` 看存活，`tail -f xxx.log` 看进度，`kill PID` 真杀。

### 坑 #9：多行命令粘贴断裂（`\` 续行符陷阱）

**现象**：粘贴命令后"什么也没发生"，但 shell 打了 `[1] PID` 让人以为已启动。

**原因**：多行命令粘贴时合并成一行，`\ ` 变成**转义空格**，argparse 报
`unrecognized arguments` 秒退——而后台符号让报错一闪而过。

**解法**：交付/执行的命令一律写成单行。

### 坑 #10：双进程写同一个文件

**现象**：日志乱码、结果文件损坏风险。

**原因**：重复启动了同名评测进程，两个进程同写一个日志/结果文件。

**解法**：**启动前先 `pgrep -af xxx.py` 确认无同名进程**；本次事故靠
"杀新留旧"无损恢复。

## 五、坑的元规律（本章真正想教的东西)

把 10 个坑放在一起看，能提炼出五条元规律：

1. **昂贵资源要有生命周期管理**——显存、API 额度、GPU 时都是；用完即释放，
   错峰使用（坑 #4、两阶段评测）。

2. **落盘粒度决定事故损失**——设计任何长任务，第一个问题是"死在第 N 步，
   前 N-1 步还在吗？"（坑 #7）。

3. **默认值是隐形炸弹**——`enable_thinking=True`、"最后统一写盘"、
   无条件覆盖的异常处理，全是默认/顺手写法惹的祸（坑 #5、#6、#7）。

4. **异常路径要用"最小破坏"原则写**——重试、跳过、兜底标记都可以，
   但绝不覆盖已成功的产出（坑 #6）。

5. **对反常结果保持怀疑**——23% 的 base、260 张表、一秒结束的"后台任务"，
   反常即有妖，追根前不下结论（坑 #5、#2、#9）。
