## 1. 错题归因：一切增强的前置

系统到 85% 之后，往哪继续投入？项目的答案：**先归因，再动手**。

关键数字缺口：hr_route 的 **evidence 96.2% vs acc 85%——中间 ~11pp 是
"检索已把料备齐、答案仍然错"的区域**，里面混着四种性质完全不同的错误：

```
                     ~11pp 落差解剖
        ┌──────────────┬──────────────┬──────────────┬──────────────┐
        │  内在幻觉      │  表格读数错   │  双问半对      │  裁判冤案     │
        │ 上下文有对的数  │ 线性化质量差  │ 复合题只答对一半│ 答对但被判 0  │
        │ 模型偏编别的   │ 看得见读串行  │ 被二值严判判 0 │ (#36 有实锤)  │
        ├──────────────┼──────────────┼──────────────┼──────────────┤
        │ → 数字回查     │ → 表格线性化  │ → 子问题分解   │ → 裁判校准    │
        │   校验器       │              │              │              │
        └──────────────┴──────────────┴──────────────┴──────────────┘
```

做法：筛出全部 `evidence=1 & judge=0` 的错题，人工逐题标注四分类，
**占比表直接决定下一步做哪个**——这是全项目一以贯之的方法论：

> **先测量 → 数据决策 → 验证。** 不做"感觉上应该有用"的优化。

## 2. 幻觉治理：内外分治

"幻觉"不是一个问题，是两个问题，解法完全不同：

| 类型 | 定义 | 状态 |
|---|---|---|
| **外在幻觉** | 上下文根本没有相关信息，模型硬编 | ✅ 已闭环：30 题库外测试拒答率 100%、幻觉率 0%（05 章） |
| **内在幻觉** | 上下文里有正确信息，模型忽略或编了别的 | 藏在 ~11pp 落差里，待归因确认占比 |

针对内在幻觉的设计方案——**数字回查校验器**：

```
生成的答案："2025 年净利润为 -9,376 万元 [2]"
                     │
                     ▼  纯字符串匹配（零 API 成本）
     答案中每个金额/百分比 ∈ 检索上下文？
                     │
          ┌──────────┴──────────┐
        在 ✅                  不在 ❌
        放行              标注 "⚠️ 该数字无出处"
```

为什么选它而不是 CoVe（让 LLM 再自校验一轮）？**便宜一个数量级**（几十行代码
vs 每题多一次 LLM 调用），且"金融场景数字必须有出处"的设计动机自解释。
先上破车，量化拦截率，不够再升级。

配套动作：生成 prompt 的"可引用来源"改成"**必须**引用 [N]"——顺带补上
"引用准确性从未验证过"的旧账。

## 3. 索引增量更新：场景特性决定架构

通用的"向量库增删改"很复杂，但**先看场景**再设计，问题会塌缩成简单版本：

> 年报是**不可变快照**——2025 年报发布后永远不变；更新形态天然 append-only
> （新年份/新公司）；真正的"改"只有勘误，且以**整份文档替换**出现。
> → **更新单元是文档，不是 chunk。**

| 操作 | 方案 |
|---|---|
| 新增 | 新文档切块向量化 → `faiss.add()` 追加 + records 追加；BM25 是内存结构直接重建（秒级） |
| 删除 | FAISS 平铺索引不支持真删 → **软删除**（records 标 `deleted`，检索后过滤），定期 compact 全量重建 |
| 修改 | = 软删旧文档全部 chunk + 追加新文档（**永不改单个 chunk**） |

> 📝 为什么平铺索引不支持真删：它本质是一个连续数组，中间抠掉一条会导致后续
> 编号全部错位（而编号正是回 records 取原文的钥匙）。FAISS 是什么、索引类型
> 怎么选，见 [03 章 §2.1+ 补课](03-检索篇-四级火箭.md)。

增量账本也便宜：`manifest.json` 补一个 `file → content_hash → chunk_id 区间`
映射——哈希变了就文档级替换，没变就跳过。

> 💡 当前规模（4461 块）全量重建只要 CPU 十几分钟，**"不过度工程"本身就是
> 当前的正确方案**；上面的设计是"规模上来之后怎么办"的预案。

**时效治理**顺着同一思路：不删旧年份，做**时间感知检索**——chunk 元数据补
`report_year`（文件名自带日期，零成本）；query 带年份→硬过滤；不带→默认最新
且答案强制标注"数据来自 XX 年报"。

## 4. 决定"不做"的技术（价值不亚于做了的）

### 4.1 GraphRAG：评估后不做（三层论据）

GraphRAG（把语料抽成实体-关系图再检索）很火，但评估后判定**不适配本场景**：

1. **查询模式不匹配**：GraphRAG 的价值在跨文档多跳推理与全局摘要；本项目 95%+
   的查询是"单公司单指标"，公司路由已把检索切到单文档内，**零跳**。recall 数据
   坐实 doc@20 = 100%——"找到正确文档"根本不是瓶颈，而图恰恰是用来解决
   找文档/找关系的；
2. **成本与更新冲突**：建图需 LLM 抽取全量实体关系（token 成本数十倍）；增量更新
   是 GraphRAG 最大痛点（新文档要合并子图、重算社区聚类），与 §3 的 append-only
   更新需求正面冲突；
3. **唯一像图的场景有更便宜的替代**：年报里真正的图状数据只有关联交易/股权穿透
   网络——强 schema 数据，结构化抽取成表 + 过滤查询，比图数据库实惠得多。

### 4.2 HyDE / Multi-Query / Step-back：动机被实验否定

这些 query 增强技术的共同动机是"用户问法与文档语域不匹配"。05 章的口语化改写
实验就是动机检验：口语化提问 acc 不降反升（+2.5pp）——**动机不成立，不做**。
唯一保留的候选是**子问题分解**（考卷双问句多，复合题证据可能分散在多个 chunk），
但也设了触发条件：**仅当错题归因显示"双问半对"占大头时才做**。

> 📌 **面试口径**（两句话背下来）：
> "GraphRAG？按查询模式和 recall 数据评估过，不适配此场景。"
> "HyDE？做过口语化鲁棒性实验，动机不成立——测过所以没做。"
>
> 这套"每个不做的技术都有一个否定实验/数据"的方法论，比堆砌名词高级得多。

## 5. 生产化补丁清单（决策已定，按需实现）

| 补丁 | 设计 |
|---|---|
| **评测回归集** | 100 题主评测 + 30 题拒答考卷固化为回归集；任何检索/prompt/索引改动后必跑，**acc 掉 >3pp 或幻觉率 >0 即回滚**——CI 思维，现有脚本零改动即可充当 |
| **在线监控** | 检索 top-1 分数分布漂移（骤降 = 索引或查询分布变了）；拒答率监控（骤升 = 库覆盖不足） |
| **安全** | 用户 query 拼进 prompt 前清洗（防 prompt 注入）；反馈回路落库的 query 需脱敏 |
| **反馈回路** | 用户点踩 → 落库 query + 命中 chunk_id → 沿 `file + chunk_idx` 溯源到 PDF 原页（records 结构已具备溯源链） |
| **成本账** | 本地 4B：零 API 成本、acc 83.3% vs API：acc 86.7% —— "精度损失 ~3pp 换私有化 + 零成本"是现成结论 |
| **演示层** | Gradio 页面：提问 → 召回片段（公司/双路排名/精排分）→ 带引用答案，~100 行 |

## 6. 全项目方法论总结（毕业寄语）

回看 7 章，这个项目真正可迁移的不是某个技术，而是一套工作循环：

```
        ┌─────────────────────────────────────────┐
        │                                         │
        ▼                                         │
   ① 测量现状 ──▶ ② 归因瓶颈 ──▶ ③ 最小改动 ──▶ ④ 同一份考卷验证
   (基线 50%)     (数字query翻车)  (加 BM25)      (67%，+17pp 保留)
                                                  │
                              涨分保留 / 不涨回滚 ◀┘
```

对应到具体决策：

| 环节 | 实例 |
|---|---|
| 测量先行 | 先跑 vec 基线，才知道 50% 的痛 |
| 归因驱动 | vec 低分归因到"考卷缺归属"→ 先修数据再优化算法 |
| 最小改动 | 公司路由 ~40 行 > 换一个更大的向量模型 |
| 同卷验证 | seed=42 的 100 题贯穿所有实验，逐题可对比 |
| 诚实记录 | 负结果（LoRA 零增益）、口径限制（chunk 级 n=21）、冤案（#36）全部如实入档 |
| 否定实验 | GraphRAG / HyDE 的"不做"都有数据背书 |

> **最后一句话**：RAG 系统的竞争力不在用了多少种技术，而在**每一个技术决策
> 都有自己的数据**。愿你做的下一个系统，也经得起"为什么"的三连问。
