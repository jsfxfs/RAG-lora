# 04 · 生成篇：本地模型 vs API vs LoRA

> **难度**：⭐⭐⭐
> **学完你能回答**：检索做好后生成器还重要吗？4B 本地模型能替代商用 API 吗？
> 为什么 LoRA 微调对 RAG 生成没有增益——以及为什么这个"负结果"反而最有价值？

---

## 1. 实验想回答的两个问题

检索消融曲线（50→67→77→85）跑出来之后，立刻有两个尖锐的追问：

1. **这条曲线是检索的功劳，还是 DeepSeek 这个生成器的偶然偏好？**
   —— 换个生成器，增益还在吗？
2. **LoRA 微调过的模型放进 RAG 里，会不会更强？**
   —— 花了训练成本的 sft_rank16，在开卷场景下值不值？

于是设计了三方对比：

| 生成后端         | 说明                                                       | 跑在哪                        |
| ---------------- | ---------------------------------------------------------- | ----------------------------- |
| **API**    | DeepSeek-V4-Flash（商用大模型）                            | 山大代理                      |
| **base**   | Qwen3-4B 原始模型                                          | 本地 16G 卡 1，bf16，贪心解码 |
| **rank16** | Qwen3-4B + LoRA(sft_rank16)（用 A 侧 7078 条 QA 闭卷训练） | 本地 16G 卡 3                 |

**控制变量**：同一份考卷（seed=42 的 100 题）、同一套检索（hr / hr_route 两档）、
**同一个裁判**（统一 DeepSeek API 判分，保证三组分数可比）。

---

## 2. 结果一：检索增益跨模型复现（最硬的结论）

净 acc（排除 OOM 题后的公平子集，"API 同子集"= API 在完全相同题目上的成绩）：

| 配置     | base            | rank16          | API 同子集      |
| -------- | --------------- | --------------- | --------------- |
| hr       | 72.5%           | 70.8%           | 79.1%           |
| hr_route | **83.3%** | **82.6%** | **86.7%** |

看 hr → hr_route 的**路由增益**：

```
            hr ──▶ hr_route
base      72.5% ──▶ 83.3%   (+10.8pp)
rank16    70.8% ──▶ 82.6%   (+11.8pp)
API       79.1% ──▶ 86.7%   (+7.6pp)
                            
三个完全不同的生成器，增益全部复现 ✅
```

**含义**：消融曲线反映的确实是**检索质量**，不是某个生成器的偶然偏好。
换任何模型，检索优化的收益都在。（05 章的 recall@k 从检索侧再次独立验证了这一点。）

---

## 3. 结果二：LoRA 对 RAG 生成零增益（诚实的负结果）

### 3.1 数据

- 净 acc：rank16 与 base 两个配置上**净差 < 2pp**；
- 逐题胜负（双方都作答的题）：
  - hr：base 独对 8 题 / rank16 独对 7 题 → 打平
  - hr_route：base 独对 4 / rank16 独对 4 → **完全打平**

### 3.2 为什么？闭卷 vs 开卷的本质

```
LoRA 训练时干的事：闭卷背书              RAG 推理时考的事：开卷阅读理解
                                    
  Q: 中简科技主营业务？                   [检索片段已经把答案放在眼前]
  A: 高性能碳纤维...                     Q: 威力传动净利润？
     ↓                                  A: 只需要"读出来"
  把事实压进模型参数                        ↓
                                        这个能力 base 本来就有
```

LoRA 是按**闭卷问答**训的——往参数里塞事实。而 RAG 把答案直接放进上下文，
考的是**阅读理解**，这是 base Qwen3-4B 出厂就会的能力。两者训练目标和使用
场景根本没对上，所以没有增益。

### 3.3 LoRA 的真实价值在哪（不是没用，是分工不同）

| 场景                                      | rank16 vs base                                                  |
| ----------------------------------------- | --------------------------------------------------------------- |
| **闭卷**问答（此前 eval_rank 实验） | rank16**远超** base ✅                                    |
| **开卷** RAG 生成                   | 打平                                                            |
| **答案风格**                        | 中位长度**73 vs 206 字符**——学到了"直接给答案不啰嗦" ✅ |

> 📌 **面试价值**：负结果比正结果更能证明你懂原理。"LoRA 管参数化知识和风格，
> RAG 管非参数化事实，两者正交"——这句话背后是花 GPU 时和 API 费跑出来的数据。

> 📝 严格地说，"LoRA 零增益"是口语化说法——被检验的其实是 **SFT 学到的内容**
> （闭卷事实 + 简答风格）在开卷场景下无增益；LoRA 只是让这次训练变便宜的手段。
> 换成全参微调训同样数据，结论大概率不变。概念辨析见文末附录 Q3；微调的完整
> 价值图谱（不止风格）见附录 Q1。

## 4. 结果三：4B 本地模型 ≈ API 的 96%

hr_route 同子集：**base 83.3% vs API 86.7%**，差距仅 ~4pp（约 3~4 题），
且集中在长表格数值读数题。

```
检索质量差时：            检索质量好时（hr_route）：
生成器差距被放大           生成器差距缩到 ~4pp
                      
API    ████████ 77%      API    █████████ 86.7%
base   ██████   66%      base   ████████▊ 83.3%
      （hr, 全量口径）           4B ≈ API 的 96%
```

**含义（本项目最重要的架构结论）**：

> **RAG 系统的瓶颈在检索，不在生成。** 检索拉满后，用 4B 本地小模型替换商用 API，
> 精度损失 ~4pp，换来的是**私有化部署 + 零 API 成本 + 数据不出域**——
> 金融场景这笔交易非常划算。

三方交叉验证补充（hr_route 共同 89 题）：三方全对 68 题、全错 5 题、仅 API 对 6 题。
那 5 道全错题是什么？**长表格数值题**——数据侧（表格线性化）的问题，
换再强的生成模型也救不回来，进一步佐证"瓶颈不在生成"。

## 5. 值得注意的实验设计细节

### 5.1 OOM 题的公平处理

本地两张 16G 卡各有 9~11 题 CUDA OOM（最长上下文的表格题）。处理方式教科书级：

- **全量口径**：OOM 计 0 分（压低本地绝对分，如实呈现）；
- **净 acc 口径**：排除 OOM 题，并让 API 也**只在相同子集**上算分（公平对比）；
- 两张卡 OOM 的是**同一批题**（同考卷同检索），所以 base vs rank16 内部对比不受影响；
- 顺带发现：这批题 API 也只对 5~7/10——本来就是考卷里的困难题。

> 💡 **通用经验**：有缺失数据时，报两个口径（含缺失的保守值 + 排除缺失的公平值），
> 并保证对比双方在同一子集上比。只报对自己有利的口径是自欺。

### 5.2 隐蔽大坑：Qwen3 的思考模式

首轮实验 base 只有 23%、rank16 却正常——差点得出"LoRA 大幅提升 RAG"的**错误结论**。

真相：Qwen3 的 chat template 默认 `enable_thinking=True`，base 的回答是大段
`<think>...`，512 token 上限内经常还没想完就被截断；而 rank16 学过 QA 数据的
简答风格，**自发不 think**，于是显得"强"。

修复一行：`apply_chat_template(..., enable_thinking=False)`。base 分数立刻恢复正常，
"LoRA 增益"随之消失。

> 📌 **教训**：对比实验里任何一方有异常低分，先怀疑实验设置，再下结论。
> 一个默认参数差点制造一个错误的正结果。

### 5.3 两阶段评测：GPU 和 API 的活分开干

本地评测 = GPU 生成答案 + API 裁判打分。若混着跑，GPU 显存被生成模型占着，
API 打分期间整卡陪跑浪费。`eval_retrieval.py` 的方案：

```
--stage gen    纯 GPU：批量生成全部答案 → 落盘 → 释放显存
--stage judge  纯 API：读答案批量打分（零 GPU 占用）
--stage all    先集中干完 GPU 的活 → 打印"显存已释放" → 再并行打分
```

配套的显存生命周期管理（检索模型用完即释放）在 06 章踩坑篇详述。

## 6. 端到端延迟账本

| 环节                | 耗时                               |
| ------------------- | ---------------------------------- |
| 检索（vec/hybrid）  | <0.1s                              |
| 检索（+精排，GPU）  | ~0.6s                              |
| 生成（API）         | ~3-10s（经验估算，受代理负载影响） |
| 生成（本地 4B GPU） | ~5-15s（经验估算）                 |

**延迟瓶颈在生成侧**，检索优化几乎不影响响应时间——又一个"检索增强很划算"的注脚。

## 7. 本章小结

| 结论               | 一句话                                                 |
| ------------------ | ------------------------------------------------------ |
| 检索增益跨模型复现 | +8~12pp 在三个生成器上全部成立，消融曲线是检索的功劳   |
| LoRA 对 RAG 零增益 | 闭卷训练 vs 开卷考试，目标没对上；LoRA 价值在闭卷+风格 |
| 4B ≈ API 96%      | 检索拉满后瓶颈不在生成，本地小模型可换私有化+零成本    |
| 剩余错误在数据侧   | 三方全错题集中在长表格——表格线性化是下一个优化点     |
| 实验方法           | 同考卷同裁判、OOM 双口径、异常低分先查设置             |

## 附录：微调知识三问（学习追问补充，2026-07-29）

> 📝 本附录源自学习过程中的三个真实追问，补全正文"LoRA 零增益"结论容易引发的误解。

### Q1：微调对 RAG 没增益，那微调到底有什么价值？只是学风格/格式吗？

远不止。完整价值图谱（①②本项目实测验证，其余为通用经验）：

```
微调的价值
├─ ① 知识注入（闭卷）      封闭域稳定知识 ← eval_rank 实验：闭卷 rank16 远超 base
├─ ② 风格/格式对齐         答案中位长度 73 vs 206 字符，风格"焊死"不占 prompt
├─ ③ 行为塑造             指令遵循、拒答边界、思考模式控制
├─ ④ 结构化输出可靠性      JSON/工具调用：prompt 约束 ~95% 到头，微调拉到 99%+
├─ ⑤ 小模型蒸馏大模型      用大模型输出训小模型 → 私有化 + 百倍降本
├─ ⑥ 领域语言理解          医疗/法律/金融黑话的语义偏移修正
└─ ⑦ 检索侧微调（易忽略）  微调 embedding/reranker 而非生成模型 → 见 Q2
```

决策速查：**缺会变的事实 → RAG；缺稳定的行为（风格/格式/拒答/工具调用）→ 微调；
缺检索质量 → 微调检索器或上混合检索+路由；要大模型能力但要私有化 → 蒸馏。**
一句话：RAG 管"知道什么"（外置、可更新），微调管"怎么表现"（内化、稳定）。

### Q2：embedding/reranker 怎么微调？reranker 不是个方法吗？

先纠正：**"精排"这个动作是方法，但执行它的 bge-reranker-large 是个 ~0.3B 的
交叉编码模型**（BERT 类，有权重文件，在 `models/BAAI/` 下）——和 Qwen3-4B 一样
可以被训练。它们是在通用语料上预训练的，对"归母净利润"这类年报黑话的检索
模式存在垂域微调空间。

怎么训：训练样本 = **(query, 正例块, 若干难负例块)**。embedding 用对比学习
（InfoNCE，把正例拉近、负例推远），reranker 用二分类（query⊕块 → 1/0）。
核心技巧是**难负例挖掘**：用现有检索器跑 top-50，取"排得靠前但不是 gold"的块——
本项目 recall 实验发现的"reranker 跨公司串扰块"就是天然的最佳难负例。

本项目的标注其实现成：query = QA 的 instruction（A 侧 7078 条可当训练集），
正例 = 答案里的【块N】引用（recall 实验已核实 N-1 无错位），工具链用 BAAI 官方
FlagEmbedding，0.3B 量级单卡可训；验证闭环用现成的 recall@k 脚本（零 API）。
**但按"先测量再决策"原则当前不做**：hr_route 的 chunk@6 已 81%、doc@6 已 100%，
错题大头在生成读表与裁判严判，不在检索——它适用于语料规模更大、路由等硬过滤
用不上、或 chunk 级 recall 长期卡低位的场景。

### Q3：LoRA 和 SFT 都是微调手段？DPO 是微调的目的？

都不对——它们在**两条正交的轴**上，自由组合：

```
轴①：学什么（训练范式/损失函数）        轴②：怎么改参数（更新方式）
────────────────────────          ────────────────────────
继续预训练（补领域知识）                  全参微调（所有权重都动）
SFT（模仿标准答案，数据是 QA 对）        LoRA（冻结原权重，只训低秩增量）
DPO/RLHF/KTO（对齐偏好，数据是        QLoRA（4bit 底座 + LoRA）
  "指令+好答案+差答案"三元组）           Freeze（只解冻后几层）
```

- 本项目 `sft_rank16` = **SFT（轴①）× LoRA rank=16（轴②）**；LLaMA-Factory
  配置里就是两个独立参数：`stage: sft/dpo/kto` 和 `finetuning_type: lora/full/freeze`；
- SFT 和 DPO 是同轴兄弟：SFT 只见过"对的答案"，DPO 能表达"两个都通顺但我更要
  简洁的那个"（它是 RLHF 的轻量替代，不需要单独的奖励模型）；目的是"对齐偏好"，
  DPO 只是实现这个目的的方法之一；
- LoRA 在另一轴上：不改变学什么，只决定用多少显存/存储代价写进参数；train 完的
  adapter 几十 MB 可插拔——本章 base vs rank16 对比实验靠 `--no-adapter` 一个开关
  切换，正是这个可插拔性的好处。

> 📌 记忆句：**轴①决定模型学什么，轴②决定用多少代价学；"目的"永远在轴①的
> 数据和损失函数里。**
