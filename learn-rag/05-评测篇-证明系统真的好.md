## 1. 为什么评测值得单独一章

大多数 RAG 教程止步于"跑通了、答对了"。但一个内行面试官会连环追问：

> "85% 是怎么判出来的？裁判可靠吗？"
> "考卷是模型自己出的吧？措辞贴原文，检索是不是占便宜了？"
> "问它库里没有的东西，会胡编吗？"
> "acc 涨了，你怎么证明是检索的功劳而不是碰巧？"

**每一问都能一句话问穿一个没做评测效度的项目。** 本项目把这四问变成了四个实验，
统称"评测效度加固"（产物在 `eval_validity/` 目录）：

```
质疑                          实验                        结果
────────────────────────────────────────────────────────────
"acc 是碰巧涨的吧？"      →   recall@k 直算              chunk@6 与 acc 同步 ✅
"会胡编吗？"             →   30 题库外拒答测试           拒答 100% 幻觉 0% ✅
"考卷偏心检索吧？"        →   异家族模型口语化改写重考     +2.5pp，皮实 ✅
"裁判可靠吗？"           →   第二裁判交叉校准            （进行中）
```

## 2. 主评测怎么搭：三个互补的指标

### 2.1 acc：LLM-as-Judge 二值判分

让另一个 LLM（DeepSeek）当裁判，对照参考答案给模型输出判 1/0：

```
┌─ 判分规则（严判）─────────────────┐
│ 数值错 / 拒答 / 答不全   → 0      │
│ 表述不同但事实一致        → 1      │
└─────────────────────────────────┘
```

**为什么用 LLM 当裁判？** 3108 条 QA 人工判不动；字符串精确匹配又太脆
（"净利润为-9376万" vs "-93,767,876.98 元"是同一个答案）。LLM-as-Judge
是规模化评测的现实选择——但它引入了新的信任问题（见 §6）。

### 2.2 evidence：不依赖裁判的检索代理指标

> 一句话：参考答案里那些"一看就是实质数据"的大数字，有没有原样出现在检索到的上下文里？

**怎么判**（三步，纯字符串匹配，零 API 成本）：

1. 用正则从**参考答案**里抠出所有数字；
2. 只留 **≥4 位**的（去掉千分位逗号后比），逐个到检索上下文里找；
3. 全找到 → 命中（1）；参考答案压根没数字 → 这题不适用（不计入分母）。

**为什么这么设计**：

- **为什么只看 ≥4 位**：1~3 位的数字满天飞（年份"2025"、条目号"第 9 条"、百分比"31%"），
  就算撞上也是巧合，说明不了检索找对了片段；而营收/成本/总资产这类**实质财务数据**动辄七八位，
  一个七位数能在上下文里精确出现，几乎可断定"检索确实召回了含答案的原文块"，误判率极低；
- **为什么去千分位逗号**："6,053,710,043" 和 "6053710043" 是同一个数，格式差异不能算没命中；
- **为什么要它**：acc 依赖 LLM 裁判，而裁判本身可能有偏（见 §6）；evidence **完全独立于裁判**，
  是一把不花钱、不看裁判脸色的尺子，专门回答"检索把料备齐了没有"。

> 🏭 **这不是我们发明的**：工程上"答案能否被检索上下文支撑"是一个标准指标，
> 业界叫 **Faithfulness（忠实度）/ Groundedness（接地性）**，属于 RAG 评估三大件之一，
> RAGAS、TruLens 等框架都有自动化实现。我们这里用"大数字匹配"做了个零成本的特化近似——
> 完整的行业对标见 **§7**。

evidence（检索备料）和 acc（最终答对）之间的落差，就是**生成侧的损耗**：

```
hr_route:  evidence 96.2% ────────── acc 85.0%
                        └── 中间 ~11pp = 检索已命中但答错
                            （表格读数错 / 双问半对 / 裁判冤案 / 内在幻觉）
```

这个落差直接指导了下一步优先级：**瓶颈已从检索转移到"生成读表 + 裁判严判"**，
再堆检索技术已无收益。

### 2.3 recall@k：检索命中率直算（评测 QA 带 source 字段后才解锁）

两级口径（`@k` = 检索返回的前 k 个块里；k 取 6 和 20 两个观察点——6 是最终进
prompt 的块数，20 是精排前的候选池大小，所以 @20 量召回、@6 量排序）：

以一道题为例（“威力传动 2025 年营收是多少？”，参考答案标注数字出自威力传动的**【块37】**）：

- **doc 级（宽）——“找对公司了吗”**：top-k 的 k 个块里，只要有**威力传动这家公司的任一块**（【块12】【块37】都算）就命中；gold 公司 = 标准答案对应的那家公司；
- **chunk 级（严）——“找对那一段了吗”**：top-k 里必须出现**参考答案引用的那唯一一块【块37】**才算命中；捞到了威力传动的别的段但没【块37】，则 doc 命中、chunk 未命中。

两者是包含关系：**chunk 命中 → 必 doc 命中；但 doc 命中不一定 chunk 命中**（找对公司不等于捞到含答案的那段）。下面的数据会看到：“找对公司”早已饱和，真正难的是把那唯一正确的一段排进前 6。

| 配置     | doc@6          | chunk@6         | chunk@20        | acc             |
| -------- | -------------- | --------------- | --------------- | --------------- |
| vec      | 93.0%          | 42.9%           | 47.6%           | 50.0%           |
| hybrid   | 94.0%          | 52.4%           | 66.7%           | 67.0%           |
| hr       | 92.0%          | 66.7%           | 66.7%           | 77.0%           |
| hr_route | **100%** | **81.0%** | **85.7%** | **85.0%** |

四个高信息量发现：

1. **chunk@6 与 acc 几乎同步**（42.9→52.4→66.7→81.0 vs 50→67→77→85）
   ——acc 增益确实来自检索命中率，这是消融曲线最干净的注脚；
2. **找对公司 ≠ 找对块**：doc@20 全档 100%（早饱和），难的是把正确的块排进前 6；
3. **精排与路由的分工被切开**：hybrid→hr 的 chunk@20 不变而 chunk@6 +14pp
   （精排只管排序）；hr→hr_route 的 chunk@20 +19pp（路由改善候选集本身）；
4. **意外发现 reranker 跨公司串扰**：hr 的 doc@6（92%）反而低于 hybrid（94%）
   ——精排会把别家的相似块顶进前 6，路由恰好根治（hr_route doc@6=100%）。

> ⚠️ **统计口径的诚实**：chunk 级分母只有 21 题（答案带【块N】标注的那部分），
> 区间宽（±~20pp），**只引用趋势不引用绝对值**；doc 级分母 100 可直接引用。
> ——小样本指标要主动声明置信度，这是数据素养的体现。

## 3. 加固一：拒答/幻觉评测（金融场景的生死线）

### 3.1 问题

主考卷 100 题**全部是有答案的题**——从没测过"库里没有的问题，模型会不会硬编"。
金融场景这是致命项：编一个不存在的收购案比答错一个数字严重得多。

### 3.2 考卷设计（值得细读，出题比跑分难）

30 题库内无答案的问题，两类各 15 题：

| 类型     | 设计                                                                              | 例子                         |
| -------- | --------------------------------------------------------------------------------- | ---------------------------- |
| 库外公司 | 茅台/宁德等知名 A 股，不在 B 侧 15 家也不在 50 家池里                             | "贵州茅台2025年营收？"       |
| 编造事项 | B 侧 15 家每家 1 题，**专挑"存在必披露"的大事**——库里真没有就说明真没发生 | "山西焦煤宣布关闭全部煤矿？" |

**硬负例**（最见功力的设计）：造题后对 B 侧语料做关键词自检，发现 3 题的关键词
真的在语料里出现——顺势保留为"硬负例"。最毒的一题：语料释义表里真有
"Enchem 指 韩国亿恩科"，看模型会不会顺着这个真实关键词编出假事件。

### 3.3 结果

| 范围 | n  | 拒答率         | 幻觉率       |
| ---- | -- | -------------- | ------------ |
| 全部 | 30 | **100%** | **0%** |

- 30 题**全量人工复核**与裁判一致（数字不依赖裁判可信度）；
- 硬负例全过：#23 检索召回了白银有色**真实的**巴西铜金矿收购，模型准确区分
  "这不是智利锂矿"，没有张冠李戴；#21 甚至引原文反驳编造的前提；
- 路由零误触发：库外公司 15 题全部 routed=None；
- 且这是在**未加任何防幻觉提示词**的情况下达成的——现有 prompt 的
  "严格基于片段"已够用，预留的 --guard 对照组无需再跑。

> ⚠️ **这是“测量”不是“防护”**：本节只是**测试**了模型面对无答案问题的表现，
> 并**没有实现任何专门的拒答/防幻觉机制**。100% 拒答、0% 幻觉是“基座模型 + 现有
> ‘严格基于片段’prompt”的**原生表现**，不是我们加固出来的。好结果值得记录，
> 但必须说清它来自基线行为而非专门设计。真要工程加固，还有 guard 提示词、
> 生成后数字回查校验、置信度阈值拒答等手段未做——目前的结论是“测过，暂不需要”，
> 而非“已经做了防护”。

> 📌 **口径诚实**：此评测生成器是 API；本地 Qwen3-4B 的拒答能力未测（当时无卡），
> 如被问可如实说明。——知道自己的结论边界在哪，和结论本身一样重要。

## 4. 加固二：口语化改写测试（切断"考卷近亲繁殖"）

### 4.1 质疑

考卷 QA 由 DeepSeek 从 chunk 生成 → 措辞贴原文 → 检索占便宜；
裁判又是 DeepSeek → **出题人、考生、阅卷人是一家子**。85% 可能高估真实用户
口语提问时的表现。

### 4.2 实验设计

```
主考卷 100 题 ── Random(7) 二次抽样 40 题（原 acc 82.5%）
        │
        ▼  改写者：Kimi-K2.5（异家族！与出题/答题/裁判的 DeepSeek 无亲缘）
"公司的主营业务和主要产品有哪些？"
        │
        ▼  改成散户口语（公司名/考点/参考答案不变）
"这公司到底是做啥生意的，主要卖些啥产品？"
        │
        ▼  全部人工复核（1 题歧义手修），重跑 hr_route 同口径评测
```

### 4.3 结果与决策含义

| 问法             | acc                       |
| ---------------- | ------------------------- |
| 原问法（年报腔） | 82.5%                     |
| 口语化改写       | **85.0%（+2.5pp）** |

判定线是"掉 ≤5pp 即算皮实"，实际持平略升（40 题粒度 ±1 题内，读作"无差异"）。
逐题复核翻转题：**无一例是口语化导致检索失败**。原因：hybrid 的 BM25 关键词层
和向量语义层互为兜底——口语化丢了关键词时，语义检索接住了。

**这个实验最大的价值是省掉了四个技术**：HyDE、Multi-Query、子问题分解、Step-back
这些 query 增强手段的共同动机就是"用户问法和文档语域不匹配"。本测试就是动机实验，
结论：**动机不成立，暂不做**。

> 📌 **方法论**："测过所以没做" >> "听说很火所以做了"。每一个没上的技术
> 都应该有一个否定它动机的实验。

## 5. 评测基建：这些分数是怎么"稳定产出"的

支撑以上所有实验的工程机制（细节在 06 章）：

- **固定随机种子**（seed=42 抽题）：所有配置、所有生成器考**同一份卷**，可逐题对比；
- **三级断点续存**：配置级跳过 / 每 20 题分段落盘 / 生成答案每 10 题增量存——
  进程被杀零损失；
- **结果隔离**：本地评测独立目录 `eval_local/`，与 API 结果互不污染；
- **errors 可审计**：单题失败重试 3 次、失败计 0 不中断、错误计数进结果文件
  （消融表能标注 "errors 全为 0" 就是这么来的）。

## 6. 尚未闭环的最后一块：裁判校准

已知裁判有冤案实锤：#36 答案实际正确（还额外指出年报两处数字不一致），裁判判 0；
五粮液一题模型引用了参考答案覆盖范围外的正确信息，被冗判。

**计划方案**（正在做）：用异家族 Kimi-K2.5 当**第二裁判**，对已判题独立重判，
算交叉一致率，分歧题人工仲裁 → 给出裁判噪声区间。有了噪声区间，
"85.0% vs 83.3% 差异显不显著"才有答案。

> 💡 口语化实验顺手接入了 Kimi-K2.5，第二裁判的基建已经免费就位——
> 好的实验设计会互相成就。

## 7. 对标业界：手搓评测 ↔ 标准框架

前面六节像是"自研"，其实每一件都能在成熟的 RAG 评测方法论里找到对应的标准名词。
把它们对上号，才知道自己站在什么位置——也才经得起"你这套是拍脑袋还是有依据"的追问。

### 7.1 评测要分两段：检索段 + 生成段

RAG 评测的第一共识：**别用一个端到端分数打天下**。acc 掉了，你分不清是"没检索到"还是
"检索到了没答好"。所以标准做法是拆两段各自量化。

**检索段**——沿用信息检索（IR）几十年的老指标：

| 指标        | 含义                         | 本项目                  |
| ----------- | ---------------------------- | ----------------------- |
| Recall@k    | top-k 覆盖到相关文档了吗     | ✅ §2.3 doc/chunk 两级 |
| Precision@k | top-k 里有多少是真相关       | 未单列                  |
| MRR / NDCG  | 相关块排得靠不靠前（看位置） | 隐含在精排消融，未单列  |

**生成段**——RAG 特有的 **RAG Triad（RAG 三角）**，围绕"问题 Q — 上下文 C — 答案 A"三者关系：

| 指标                                  | 问的问题                         | 本项目对应                     |
| ------------------------------------- | -------------------------------- | ------------------------------ |
| **Faithfulness / Groundedness** | 答案是否全由上下文支撑、没编造   | evidence（§2.2）+ 拒答（§3） |
| **Answer Relevance**            | 答案切不切题                     | acc 判分隐含                   |
| **Context Relevance**           | 检索的上下文有没有用、有没塞垃圾 | 精排消融隐含                   |

> 你在 §2.2 用的 evidence，正式名字就是 **Faithfulness** 的一个特化——标准做法是让 LLM
> 把答案拆成一条条论断、逐条回上下文查证据；我们把"论断"窄化成"≥4 位大数字"，
> 用字符串匹配替代 LLM，换来零成本、零裁判依赖。

### 7.2 业界都用什么工具

真实项目很少手写评测，主流开源框架：

- **RAGAS**：最流行。主打**无参考答案也能评**——LLM 自动算 Faithfulness / Answer Relevance /
  Context Precision / Context Recall 四大件，天然适合线上（线上没标准答案）；
- **TruLens**："RAG Triad"这个叫法的提出者，强调**可观测**——把每次调用的三角分数记录下来做监控；
- **LlamaIndex / LangChain 内置 evaluator**：`FaithfulnessEvaluator` 等，开箱即用；
- **DeepEval**：把指标封装成 **pytest 单测风格**，天然适合做 CI 回归（呼应路线图的"评测回归集"）；
- 
- **ARES**：训练小模型当裁判，还给统计置信区间。

### 7.3 裁判可信度：这也是一门标准学问tat

我们 §6 的裁判校准不是原创焦虑，而是 LLM-as-Judge 的**标准课题**：

- **已知偏见**：偏爱长答案、偏爱同家族模型的输出（就是 §4 的"近亲繁殖"）、打分不稳定；
- **标准对策**（我们全中）：① 换异家族模型当裁判（Kimi 切断亲缘）；
  ② 多裁判投票 / 算一致率——正式指标是 **Cohen's kappa**（两裁判）、Fleiss' kappa（多裁判），
  统称 inter-annotator agreement；③ 人工标注小集做锚点（30 题全量复核）。

### 7.4 一句话定位

| 标准框架组件            | 本项目的轻量实现                            |
| ----------------------- | ------------------------------------------- |
| Context Recall          | recall@k 直算（§2.3）                      |
| Faithfulness / 幻觉检测 | evidence 数字匹配（§2.2）+ 拒答测试（§3） |
| 裁判校准 / kappa        | 第二裁判交叉一致率（§6）                   |
| 无参考评估 / 鲁棒性     | 异家族口语化改写（§4）                     |
| CI 回归                 | 评测回归集（路线图）                        |

所以面试可以有两种讲法，都成立：

> 💡 **讲工程**："我不引重依赖，用字符串匹配 + 单一 API 裁判把 RAG Triad 的核心跑通，
> 成本可控、每个指标我都知道是怎么算出来的。"
> **讲视野**："我做的 recall / evidence / 拒答 / 裁判校准，分别对应 Context Recall /
> Faithfulness / 幻觉 / kappa 校准，只是出于成本和可控性做了轻量化。"
>
> 下一步可选：真把 **RAGAS 接进来跑一轮**，和手搓指标交叉验证——既证明轻量版可靠，又展示会用标准工具。

## 8. 本章小结：一套可复用的 RAG 评测清单

| 层       | 指标/实验                       | 回答的问题               |
| -------- | ------------------------------- | ------------------------ |
| 端到端   | acc（LLM-as-Judge）             | 最终答对了吗             |
| 检索独立 | evidence（数字匹配）            | 料备齐了吗（不依赖裁判） |
