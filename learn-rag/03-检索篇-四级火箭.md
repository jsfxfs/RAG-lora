## 1. 总览：一条消融曲线

同一份考卷（B 侧新 QA，seed=42 抽 100 题）、同一个生成器（DeepSeek API）、
同一个裁判，只改检索配置：

| 配置         | 组成                | acc             | evidence*       | 较上一档        |
| ------------ | ------------------- | --------------- | --------------- | --------------- |
| `vec`      | 纯向量              | 50.0%           | 84.9%           | 基线            |
| `hybrid`   | + BM25 / RRF 融合   | 67.0%           | 84.9%           | **+17pp** |
| `hr`       | + bge-reranker 精排 | 77.0%           | 92.5%           | **+10pp** |
| `hr_route` | + 公司路由          | **85.0%** | **96.2%** | **+8pp**  |

> \* evidence：参考答案中 ≥4 位的数字是否出现在检索上下文里——一个不依赖裁判的
> 纯检索代理指标。

⚠️ **四个配置名是累积叠加的，每一档都包含前一档的全部组件**（全系列文档的表格
都用这套名字）：

```
vec       = 纯向量
hybrid    = 向量 + BM25/RRF               （在 vec 上加混合召回）
hr        = 向量 + BM25/RRF + 精排         （在 hybrid 上加 reranker，故名 h+r）
hr_route  = 向量 + BM25/RRF + 精排 + 路由  （在 hr 上加公司路由）
```

所以读消融表时：**每行的绝对值是"叠到这一层的总成绩"，相邻两行的差值才是
新加组件的净贡献**——hr 的 77% 是"混合召回+精排"整套的成绩，精排本身的功劳
只是那 +10pp。

```
acc
85% ┤                                    ●  hr_route
    │                          ●  hr
77% ┤                    ╱
    │            ●  hybrid
67% ┤       ╱
    │   ●  vec
50% ┤
    └────┴──────────┴──────────┴──────────┴──
       纯向量     +BM25混合    +精排      +公司路由
```

**每一级都实打实涨分**。下面逐级拆：它是什么、补了谁的短板、怎么被验证的。

## 2. 第一级：纯向量检索（基线，acc 50%）

### 2.1 原理

离线把每个 chunk 用 bge 模型编码成向量存进 FAISS；在线把问题也编码成向量，
找余弦相似度最高的 top-k 块。

```
"净利润是多少" ──bge──▶ [0.12, -0.35, 0.88, ...]
                              │  和 4530 个块向量算相似度
                              ▼
                        top-6 最相似的块
```

**优点**：懂语义。"赚了多少钱"能召回"净利润"相关块，即使一个字都不重合。

### 2.1+ 补课：FAISS 是什么（前面一直在用，这里正式介绍）

**FAISS**（**F**acebook **AI** **S**imilarity **S**earch）是 Meta 开源的**向量相似度
搜索库**，只干两件事：把一堆向量存进"索引"；给一个查询向量，快速找出最相似的
top-k。可以理解为"向量数据库的裸引擎"——无服务、无网络接口，就是个 Python 库：

```python
index = faiss.IndexFlatIP(1024)   # 建索引（IP=内积，向量归一化后≈余弦相似度）
index.add(chunk_vectors)          # 存入 4530 个块向量
D, I = index.search(query_vec, 6) # 查 top-6：返回相似度 D 和块编号 I
```

两个关键认知：

- **分工**：bge 管"把语义变成向量"（模型），FAISS 管"在一堆向量里快速找最近邻"
  （引擎）。语义懂不懂是 bge 的事，找得快不快是 FAISS 的事——下面 2.2 的翻车
  全是 bge 向量区分度的问题，与 FAISS 无关；
- **FAISS 只存向量和编号，不存文本**：查到编号后要回 `records` 元数据表（块原文、
  company、source）取内容，所以架构图里两者成对出现。

**索引类型和规模匹配**：本项目 4530 块用最朴素的**平铺索引（IndexFlat）**——和每个
向量都精确算一遍，零近似损失，毫秒级搞定；百万~十亿级才需要近似索引（IVF/HNSW/PQ，
牺牲一点召回换百倍速度）。工具选型和语料规模匹配，这本身也是架构决策。

> 💡 **"拿来就用"的边界**：引擎内部（C++ 优化、SIMD）确实不用管，但引擎周围四件事
> 永远是使用者的责任：① 度量选择（用内积当余弦必须先归一化——最常见的坑）；
> ② 编号↔原文映射（自己维护 records）；③ 删除/更新（平铺索引不支持真删，见
> [07 章软删除设计](07-工程化与架构决策.md)）；④ 规模上去后换近似索引时的
> 召回/速度/内存权衡。Milvus/Qdrant 这类向量数据库产品 = 这类引擎 + 服务化外壳
> （帮你管 ②③），代价是多一个要部署运维的组件；本项目单机单人，裸 FAISS +
> 自管 records 是更简单正确的选型。

### 2.2 它为什么会翻车（真实案例）

查 **"股票代码 300904"**，纯向量 top-4 **全部跑偏**——召回的是别家公司的利润表。

原因：向量模型对**数字、代码、专有名词**的区分度天然很差。"300904" 和 "300890"
在语义空间里几乎是同一个点（都是"六位股票代码"这个概念），但对用户来说是两家
完全不同的公司。

> 📌 **规律**：向量检索擅长"模糊的语义"，不擅长"精确的符号"。金融场景两者都要。

## 3. 第二级：+BM25 混合召回（acc 67%，+17pp）

### 3.1 BM25 是什么

BM25 是经典的**关键词匹配**算法（搜索引擎用了几十年）：分词后统计词频、逆文档
频率，精确匹配打分。项目用 `rank_bm25` + jieba 中文分词，内存级秒建，零额外基建。

它和向量检索恰好互补：

|                          | 向量检索        | BM25                |
| ------------------------ | --------------- | ------------------- |
| "赚了多少钱" → "净利润" | ✅ 语义懂       | ❌ 无词重合         |
| "股票代码300904"         | ❌ 数字区分度差 | ✅ 精确命中         |
| 生僻专有名词             | ❌ 训练时没见过 | ✅ 只要出现就能匹配 |

实测：上面翻车的 query，**BM25 路第 1 名就精确命中**威力传动的"股票代码 300904"块。

### 3.2 RRF：两路结果怎么合并

两路各取 top-20 候选，用 **RRF（Reciprocal Rank Fusion，倒数排名融合）**合并：

```
score(块) = Σ  1 / (60 + rank_i)     # rank_i = 该块在第 i 路的名次
```

```
向量路 top-20        BM25 路 top-20
 1. 块A               1. 块C
 2. 块B               2. 块A
 3. 块C               3. 块F
   ...                  ...
      ╲               ╱
       RRF (rrf_k=60)
            │
            ▼
  块A: 1/(60+1) + 1/(60+2) = 0.0325   ← 两路都靠前，融合后最高
  块C: 1/(60+3) + 1/(60+1) = 0.0323
```

**为什么用排名不用分数？** 向量相似度（0~1 的余弦）和 BM25 分数（无上界）量纲
完全不同，直接加权要调平衡系数；RRF 只看**名次**，天然免调参、对离群分数鲁棒。

**工程细节**：每个命中块保留 `vec_rank` / `bm25_rank` 双路排名——调试时一眼看出
这个块是谁召回的，**可解释性**在排查 badcase 时价值巨大。

## 4. 第三级：+reranker 精排（acc 77%，+10pp）

### 4.1 为什么召回了还不够：双塔 vs 交叉编码器

向量检索是**双塔结构**：问题和块**分别**编码，编码时互相看不见，只能事后比向量。
这是"为了快而牺牲精度"的设计——4530 个块的向量可以离线算好。

reranker（bge-reranker-large，~0.3B）是**交叉编码器**：把"问题+块"**拼在一起**
送进模型，每一层注意力都在做问题和块的细粒度交互，精度高得多，但每对都要现算——
所以只能用在小候选集上。

```
双塔（召回，快而糙）                 交叉编码器（精排，慢而准）
                        
问题 ──▶ 向量A ╲                   [问题 ⊕ 块] ──▶ 模型 ──▶ 相关性 0.96
              比较相似度            （逐对现算，只处理 20 个候选）
块   ──▶ 向量B ╱
```

流水线：**混合召回取 20 候选（保证"该在的都在"）→ 精排逐对打分取 top-6（保证"排在前面的是真相关"）**。

> 📝 注意："精排"这个动作是方法，但 reranker 本身是个**可训练的模型**（有权重文件，
> 和 bge embedding 一样可以用垂域数据微调提升检索命中率）——怎么微调、本项目
> 为什么暂不做，见 [04 章附录 Q2](04-生成篇-本地模型vsAPI.md)。

### 4.2 验证

> 📖 **先认识两个 recall 指标**（后面反复出现，`@k` 读作"检索返回的前 k 个块里"）：
>
> - **doc@k**：前 k 块里有没有 **gold 公司**的块——"找对公司了吗"；
> - **chunk@k**：前 k 块里有没有参考答案引用的**那一块**——"找对段落了吗"（更严）。
>   本项目 k 取 6（最终进 prompt 的块数）和 20（精排前的候选池大小）两个观察点：
>   **@20 量"召回把块找没找到"，@6 量"精排把块排没排进前排"**。

- 单例：威力传动目标块经精排后 rr=0.96 升至第 1，跑偏块被压到 0.19 以下；
- 量化（recall 直算，详见 05 章）：hybrid→hr 的 **chunk@20 不变**（候选集没变），
  **chunk@6 却 +14.3pp**——精排的功劳被干净地隔离出来：**它只负责把对的块从
  20 候选拉进前 6**。

### 4.3 代价：延迟

| 配置                  | CPU 单题        | GPU 单题        |
| --------------------- | --------------- | --------------- |
| vec / hybrid          | ~0.1s           | ~0.03s          |
| **hr（+精排）** | **4.45s** | **0.62s** |

耗时大头（~97%）全在精排逐对打分。**精排是拿延迟换精度的显式交易**——
在线场景要掂量，离线评测无所谓。

## 5. 第四级：+公司路由（acc 85%，+8pp，零延迟代价）

### 5.1 动机：15 家共库的"串扰"

15 家公司的 4530 块混在一个索引里。年报是高度同构的文本——每家都有"利润表"
"管理层讨论"，问 A 家的问题极易命中 B 家的相似块（**跨公司串扰**）。

关键观察：**问题里其实已经写明了是哪家公司**（"威力传动的…"、"股票代码300904的…"），
只是检索器不认识。那就教它认识——这就是路由，本质是**元数据过滤**：

```
query: "股票代码300904的公司2025年归母净利润"
   │
   ▼ detect_company()
   ① 先试 6 位股票代码正则 ──▶ "300904" → 代码表 → 威力传动
   ② 再试公司简称子串匹配（去空格，兼容"五 粮 液"）
   ③ 都没有 → 返回 None，行为退化为全库检索（安全兜底）
   │
   ▼ search(company="威力传动")
   向量路：faiss reconstruct 取该公司 247 块的子集精确算
   BM25 路：候选池限定在这 247 块
```

实现只有 ~40 行：建索引时顺手存两张表（company → 块 id 列表、股票代码 → company），
在线一个正则 + 一次查表。

### 5.2 为什么它"免费"

|          | 数值                                                                                    |
| -------- | --------------------------------------------------------------------------------------- |
| 准确率   | +8pp（100 题全部成功路由）                                                              |
| 延迟     | **hr 4.45s → hr_route 4.18s，反而更快**（候选池从 4530 缩到 ~250，精排负担更小） |
| 额外基建 | 无（chunk 的 company 字段本来就有）                                                     |

recall 数据还揭示了一个**精排治不了、路由恰好能治**的问题：hr 的 doc@6（92%）
反而低于 hybrid（94%）——**reranker 自己会跨公司串扰**（把别家公司的高度相似块
排进前 6）。路由从候选集层面根除：hr_route 的 doc@6 = 100%。

### 5.2+ 辨析：路由是"过滤"，不是"先搜一遍"

容易误解成"两步搜索：先搜出该公司的内容，再在里面搜答案"。实际上第一步
**不是搜索（模糊匹配，可能错），而是过滤（精确匹配，不会错）**：
`detect_company()` 只对 query 文本做正则/子串匹配，根本没碰语料库；
"company 字段等于威力传动"是查表，不存在"像不像"的问题。若第一步真是搜索，
它自身的召回误差会级联传递；而过滤只有两种结局——精确命中（247 块不多不少）
或识别不出就不过滤（安全兜底），永不引入新错误。完整链路是三层漏斗：

```
过滤 4530→247（零成本零误差）→ 召回 247→20（快而糙）→ 精排 20→6（慢而准）
越往后越贵，所以把最便宜且不会错的一步放最前——这也是延迟反而下降的原因
```

推广开来，元数据硬过滤要同时过三个门槛：

| 门槛                                                      | 本项目 company 字段                      |
| --------------------------------------------------------- | ---------------------------------------- |
| ① 标签来源确定（可能标错的"软标签"只能加权，不能一刀切） | ✅ 来自文件名，建库时抄入的确定事实      |
| ② query 端抽取可靠（抽不出就没有入口）                   | ✅ 6 位代码正则 + 简称子串，抽不出则兜底 |
| ③ 对应真实查询模式（否则是死数据）                       | ✅ "XX公司的…"占绝大多数提问            |

成本为零的确定标签（文件名能提供的，如 report_year）建库时都先落盘——存着
不亏（呼应 02 章"元数据生成时免费、事后补十倍代价"）；要花模型算力打的标签，
等有明确查询模式时再加。

### 5.3 已知局限

跨公司比较题（"A 和 B 谁的营收高"）只能识别到单家——多公司并行检索留作二期。

> 📌 **规律**：领域先验（"问题必然指向一家公司"）转化成硬过滤，收益常常吊打
> 更"聪明"的通用算法。先看数据里有什么结构可以利用，再想上什么模型。

## 6. 把四级串起来看：每级各管什么

用 recall@k 数据（05 章详述）可以把分工切得非常干净
（指标含义回顾 §4.2：doc@k=前 k 块里有无 gold 公司的块；chunk@k=前 k 块里有无
答案引用的那一块；@6=最终进 prompt 的前 6，@20=精排前的候选池）：

```
                     doc@6      chunk@6     chunk@20
vec                  93%        42.9%       47.6%
hybrid               94%        52.4%       66.7%    ← BM25 扩大了"能找到"的池子
hr                   92%(!)     66.7%       66.7%    ← 精排只管排序（@20 不动，@6 大涨）
hr_route             100%       81.0%       85.7%    ← 路由改善候选集本身
```

| 组件     | 管的事   | 一句话                         |
| -------- | -------- | ------------------------------ |
| 向量     | 语义召回 | 懂"意思相近"                   |
| BM25     | 符号召回 | 懂"字面精确"（数字/代码/专名） |
| RRF      | 融合     | 免调参合并两路名次             |
| reranker | 排序     | 把对的块从 20 候选顶进前 6     |
| 路由     | 候选集   | 用领域先验砍掉 95% 的干扰块    |

**找对公司不难（doc@20 全档 100%），把正确的那一块排进前 6 才难**——
这是整条曲线最深刻的一句话。

## 7. 动手复现

```Python
# 各级配置对比体验（RAG-lora 目录）
# ⚠️ rag_chat.py 的公司路由默认开启，想体验"纯 vec 翻车"必须加 --no-route 关掉它，
#    否则 "300904" 会被路由提前锁定到威力传动的 247 块，纯向量也能蒙过去
python rag_chat.py --no-route -q "股票代码300904的公司净利润？"           # vec：大概率翻车
python rag_chat.py --no-route --hybrid -q "股票代码300904的公司净利润？"  # +BM25：能召回
python rag_chat.py --hybrid --rerank --show-hits -q "..."               # +精排+路由（默认）：排到第1

# 完整 4 配置消融评测（API 生成+裁判，注意额度）
python -u eval_retrieval.py --configs vec,hybrid,hr,hr_route --limit 100 --workers 8
```

### 7.1 实测案例：一次真实的"三连跑"（2026-07-29）

上面前两条命令 + 默认路由版实际跑出来的结果，恰好是一条活的消融曲线：

| 运行 | 配置 | 结果 |
|---|---|---|
| 1 | vec（无路由） | ❌ 连公司都没对上，引了个来路不明的数字（-24,335,425.83，对不上威力传动任何口径） |
| 2 | hybrid（无路由） | 🟡 公司对了，但拿的是**母公司利润表**的块（-23,726,149.18），不是归母口径 |
| 3 | hybrid + 路由（默认） | ✅ `[路由] 威力传动（限定 247 块）`，命中归母净利润 **-93,767,876.98 元**（gold 答案），还主动区分了归母 vs 母公司两个口径 |

三个观察：

1. **路由的威力被单独展示**：第 3 次没开 `--rerank`，只是把候选池从 4530 砍到
   247，正确的合并报表块就自己进了 top-6——印证 §6 的 "hr→hr_route 的 chunk@20
   +19pp（路由改善候选集本身）"：**有时不需要更聪明的排序，只需要更干净的候选池**；
2. **检索好，生成也会变"聪明"**：第 3 次归母和母公司两个块同时进了上下文，
   模型才有材料主动标注口径差异——是 04 章"检索质量差时生成器差距被放大"的反面例证；
3. **API 延迟是稳定基线不是抖动**：三次生成 64.90s / 62.76s / 64.35s（`[耗时]`
   行实测），方差极小；检索仅 0.17~0.19s，与 §4.3 延迟账本吻合。交互体验上
   本地 4B（秒级）对这条代理链路是碾压性优势——"4B 替换 API"除了准确率和成本，
   还有延迟这第三重论据。

> 💡 复现提示：`rag_chat.py` 的 `[耗时]` 行会打印 路由/检索/精排/生成 各段用时，
> 自己跑一遍就能看到这些数字。
